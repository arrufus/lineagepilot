# lineagepilot-lsp

The LineagePilot language server: `lineagepilot_core` behind the Language Server Protocol, over stdio (design sections 4 and 9). The VS Code extension in `extension/` starts one server per dbt project, from the copy bundled in its VSIX.

## What it does

- **Indexes in a child process** (`worker.py`): the model-level graph first, then column lineage, each handed over as a snapshot in the cache directory. The server never parses on its event loop, and freezes its heap after each load (design section 11).
- **Runs each reader in a child process** (`readers.py`), with a time limit and a memory limit. Airflow is the first: DAG files are read as syntax only. What a reader finds is put on top of whichever graph is loaded, and is never part of a snapshot (design section 6.2; the reader contract is `lineagepilot_core/readers/contract.py`).
- **Watches** the artifacts, `dbt_project.yml`, the project's source files, `.lineagepilot/rules.yml`, the annotation file (`.lineagepilot/lineage.yml` or `airflow.yml`) and each reader's globs (for Airflow, the DAG folders) through `workspace/didChangeWatchedFiles`, with debouncing.
- **LSP features**: CodeLens, hover and diagnostics (`features.py`).
- **`lineage/*` requests** (`methods.py`): `status`, `refresh`, `graph`, `impact`, `export`, `nodesForFile`, `node`, `reviewChanges`, `airflow`, and from protocol 2 `pipelines` and `consumers`, and the `indexUpdated` notification. Params are validated against the shared schema in `protocol/` (`protocol.py` is generated from it). The server speaks protocols 1 and 2: it answers in 2, and `legacy.py` turns an answer into protocol 1 for a client that negotiated that, held in the tests to the protocol 1 schema in `protocol/v1/`.

## Modules

| Module | |
|---|---|
| `server.py` | The pygls server: initialise and protocol negotiation, handlers, diagnostics publishing, logging to the client |
| `indexing.py` | The index state machine for one project, the indexer process, staleness |
| `readers.py` | One reader's read for one project: when it runs, and what became of it |
| `worker.py` | The indexer, run as a child process; it also reads a review's baseline manifest, and runs a reader |
| `context.py` | Everything derived from one loaded graph, and column lineage on demand |
| `features.py` | CodeLens, hover and diagnostics |
| `methods.py` | The `lineage/*` requests |
| `legacy.py` | Protocol 1's answers, from protocol 2's, for a client that negotiated protocol 1 |
| `locate.py` | Files and positions: where a node or column is declared in YAML. A request that places many nodes checks each folder once (`Locator.batch`) |
| `block_yaml.py` | A quick reader for the plain block YAML dbt's files are written in, for those positions; PyYAML reads anything else, with the same answers |
| `project.py` | Re-exports the core's `dbt_project.yml` reader, which the headless CLI also needs |
| `watch.py` | What is watched, what each change means, and the debouncer |
| `protocol.py` | Generated by `protocol/generate.py`; do not edit |

`scripts/server_budgets.py` measures the server against the design's budgets (design §11), end to end, with every reader turned on and a heavy workload for each. It runs by hand, on spike S2's 5,000-model project; `--check` exits 1 when a budget is missed.

## Development

```bash
cd packages/lsp
uv sync --locked
uv run --locked pytest                          # unit and end-to-end tests, coverage gate 80%
uv run --locked ruff check . && uv run --locked ruff format --check .
python ../../protocol/generate.py --check        # after changing protocol/lineage-protocol.schema.json
```

The end-to-end tests start the server with `python -I -m lineagepilot_lsp` and talk to it over stdio with pytest-lsp, on a copy of `fixtures/pilot-shop`, and for the Change Impact Review on `fixtures/impact-shop`. To run them against the VSIX's bundled server on interpreters with nothing installed:

```bash
LP_TEST_SERVER=../../extension/bundled/tool/lsp_server.py LP_TEST_PYTHONS=/path/to/python3.10:/path/to/python3.13 \
  uv run --locked pytest --no-cov tests/test_indexing_e2e.py tests/test_methods_e2e.py tests/test_features_e2e.py tests/test_review_e2e.py
```

The server writes nothing to stdout but LSP messages. Its logging goes to the client as `window/logMessage`, and to stderr for warnings and errors.
